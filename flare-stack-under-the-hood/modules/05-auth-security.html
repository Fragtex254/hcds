门卫系统——身份验证与安全

当有人试图登录你的博客管理后台，系统怎么知道他是不是真的你？如果有人用机器人疯狂注册账号，系统又怎么拦住他？答案是：层层递进的安全检查链。

机场安检的四道关卡

想象你从进入机场到登上飞机，要经过四道检查。每一道检查不同的东西，缺一不可。

✈️

值机柜台

出示身份证——确认你有航班信息，建立基本连接

🧭

安检门

扫描行李和身体——确认你没带危险物品，是合法旅客

🚪

登机口

核对登机牌——确认你有合法身份和登机权限

🏳️

VIP 通道

检查你的会员等级——只有头等舱才能走这里

博客的安全系统也是如此——每一层检查不同的东西：身份验证（你是谁）→ 权限检查（你能做什么）→ 限流（你做了多少次）→ 人机验证（你是不是真人）。

中间件链：四层安检代码

在代码中，这四道安检叫做中间件。它们层层嵌套——就像安检门必须在值机之后，登机口必须在安检之后。

CODE 
// 第一层：建立数据库连接
export const dbMiddleware = createMiddleware({ type: "function" }).server(
  async ({ next, context }) => {
    const db = getDb(context.env);
    return next({ context: { db } });
  },
);

// 第二层：识别用户身份（通过 cookie）
export const sessionMiddleware = createMiddleware({ type: "function" })
  .middleware([dbMiddleware])
  .server(async ({ next, context }) => {
    const auth = getAuth({ db: context.db, env: context.env });
    const session = await auth.api.getSession({
      headers: getRequestHeaders(),
    });
    return next({ context: { auth, session } });
  });

认证路由：多重防护的登录入口

上面的中间件是单个检查工具。但真正使用时，它们会组合在一起形成多重防护。Hono 路由中的认证端点就是这样被保护的：

CODE 
const protectedAuthPaths = [
  "/api/auth/sign-in/email",
  "/api/auth/sign-up/email",
  "/api/auth/request-password-reset",
  "/api/auth/send-verification-email",
] as const;

protectedAuthPaths.forEach((path) => {
  app.post(
    path,
    baseMiddleware,
    turnstileMiddleware,
    rateLimitMiddleware({
      capacity: 5, interval: "1m",
      identifier: createRateLimiterIdentifier,
    }),
    rateLimitMiddleware({
      capacity: 10, interval: "1h",
      identifier: (c) => `hourly:` + createRateLimiterIdentifier(c),
    }),
    forwardAuthRequest,
  );
});

注意这里用了两层限流：短窗口（每分钟 5 次）防突发攻击，长窗口（每小时 10 次）防慢速暴力破解。这就像机场安检既限制每分钟通过人数，也限制每小时总通过人数。

一次登录请求的完整旅程

当用户点击「登录」按钮，请求要经过这些检查才能成功：

1
值机柜台：建立基础连接

baseMiddleware 注入数据库连接和认证服务，就像在值机柜台确认你的航班信息

2
安检门：人机验证

turnstileMiddleware 检查 Cloudflare Turnstile 令牌，确认你是真人操作而不是脚本

3
人流管控：短窗口限流

每分钟最多 5 次登录尝试。就像安检一次只放一定数量的人进去，防止人流过大

4
全天管控：长窗口限流

每小时最多 10 次。即使每次间隔超过 1 分钟绕过了短窗口，也会在这里被拦住

5
登机：验证密码并签发会话

全部检查通过后，Better Auth 验证密码、签发 session cookie，用户成功登录

限流的秘密武器

限流器是怎么记住「这个 IP 已经请求了 4 次」的？普通的Cloudflare Workers 是无状态的，每次请求都是全新开始。

CODE 
export const createRateLimitMiddleware = (options) => {
  return createMiddleware({ type: "function" })
    .middleware([sessionMiddleware])
    .server(async ({ next, context }) => {
      const identifier =
        getRequestHeader("cf-connecting-ip")
        || session?.user.id || "unknown";
      const uniqueIdentifier = `${identifier}:${scope}`;

      // 用 Durable Object 实现分布式限流
      const id = context.env.RATE_LIMITER
        .idFromName(uniqueIdentifier);
      const rateLimiter = context.env.RATE_LIMITER
        .get(id);

      const result = await rateLimiter
        .checkLimit(options);

      if (!result.allowed) {
        throw createRateLimitError(result.retryAfterMs);
      }

      return next();
    });
};
PLAIN CHINESE

创建一个限流中间件工厂——可以按需配置限流参数

返回一个中间件

依赖 sessionMiddleware 获取用户信息

在会话中间件之后执行

获取请求者的 IP 地址作为身份标识

如果拿不到 IP，就用用户 ID 或 "unknown"

拼上 scope 前缀，区分不同场景的限流

关键：用 Durable Object 来实现限流！

根据唯一标识创建一个 Durable Object 实例

同一个 IP + scope 总是对应同一个实例

获取这个实例的引用

向 Durable Object 查询：这个 IP 还能继续请求吗？

如果超出了限制...

抛出限流错误，告诉用户多久后才能重试

没超限，正常放行

💡
关键洞察：Durable Object 是有状态的「记忆体」

普通 Worker 是无状态的——每次请求都是全新开始。但 Durable Object 可以记住状态！限流器就是用它来追踪每个 IP 已经请求了多少次。同一个 IP 总是会路由到同一个 Durable Object 实例，就像你的专属客服只服务你一个人。
