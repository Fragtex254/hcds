发布者的签发流程

在流水线启动之前，PostService 需要先完成一系列准备工作——就像杂志主编在签发前必须确认文章存在、排好期号、盖上发刊章。

CODE 
export async function publishPost(
  context: Context,
  input: { postId: number; publishedAt?: string | null },
) {
  const post = await PostRepo.findPostById(context.db, input.postId);
  if (!post) return err("POST_NOT_FOUND");

  const slug = await ensureUniqueSlug(context.db, post.title, post.id);

  let publishedAt = post.publishedAt;
  if (post.status === "draft") {
    publishedAt = input.publishedAt
      ? new Date(input.publishedAt).toISOString()
      : new Date().toISOString();
  }

  await PostRepo.updatePost(context.db, post.id, {
    publishedAt, status: "published", slug,
  });

  const instance = await context.env.POST_PROCESS_WORKFLOW.create({
    params: { postId: post.id, isPublished: true },
  });

  return ok({ postId: post.id, status: "published" });
}

⚡
为什么立刻返回？

PostService 只负责保存数据和创建 Workflow，然后立刻返回。流水线会在后台继续运行，用户不需要等待。

发布流水线的 6 个步骤

Workflow 中的每一步都是独立的 Step，任何一步失败都不会影响其他步骤。

1
检查同步状态

计算内容的 哈希，对比旧哈希。如果内容没变，跳过整个流程。

2
AI 生成摘要

调用 Workers AI 为文章生成摘要。失败时自动重试 3 次（间隔越来越长）。

3
构建公开内容快照

对代码块做语法高亮处理，然后保存为独立的「公开快照」。读者看到的就是这个快照。

4
更新搜索索引

把文章信息加入 Orama 搜索索引，确保用户搜索时能找到它。

5
失效缓存

清除 KV 和 CDN 中的旧缓存，确保用户看到最新内容。

6
更新同步哈希

记录当前内容的哈希值，防止同一内容被重复处理。

💡
关键洞察：Workflow vs 函数调用

Workflow 是「可以暂停和重试的函数」。如果 AI 服务暂时不可用，Workflow 会自动重试 3 次（每次间隔更长），而不是直接报错给用户。整个过程是异步的，用户点击发布后不需要等待流水线完成。

三层架构

每个功能模块的核心代码都遵循同一套三层结构。就像图书馆的每个分区都有书架区、管理室和借阅台。

🗄️
数据层（data/）

只做一件事：数据库查询。不关心缓存，不关心业务逻辑，纯粹的读写操作。

⚙️
服务层（service）

编排业务逻辑 + 缓存策略。决定「先查缓存还是直接查数据库」「数据要不要做额外处理」。

🔌
API 层（api/）

请求入口。接收HTTP 请求，验证参数，然后转发给服务层。它是「薄薄的」一层——几乎不包含任何业务逻辑。

💡
关键洞察：关注点分离

关注点分离——每个代码层只做自己的事。数据层不管缓存，API 层不管业务逻辑。改动一层不会影响其他层。

服务层：缓存与业务的指挥官

这是文章模块中「根据网址查找文章」的服务层代码。注意它如何协调缓存和数据库——先查缓存，缓存没有才去数据库。

export async function findPostBySlug(
  context: Context,
  slug: string,
) {
  const version = await CacheService.getVersion(context, "posts:detail");
  const cacheKey = [version, "post", slug] as const;

  const post = await CacheService.get(
    context,
    cacheKey,
    PostWithTocSchema,
    async () => {
      const post = await PostRepo.findPostBySlug(context.db, slug);
      if (!post) return null;
      if (post.publicContentJson) {
        const { publicContentJson, ...rest } = post;
        const content = contentSchema.parse(publicContentJson);
        return { ...rest, content, toc: generateTocFromContent(content) };
      }
      const content = await highlightCodeBlocks(post.contentJson);
      const { contentJson, ...rest } = post;
      context.executionCtx.waitUntil(
        PostRepo.updatePublicContentSnapshot(context.db, post.id, content),
      );
      return { ...rest, content, toc: generateTocFromContent(content) };
    },
  );
  return post;
}

核心机制：读穿缓存

读穿缓存是最常用的缓存模式。先查缓存，命中就返回；没命中就去数据库查，顺便把结果存到缓存里。下次就不用查数据库了。

CODE 
export async function get<T>(
  context: BaseContext & { executionCtx: ExecutionContext },
  key: CacheKey,
  schema: T,
  fetcher: () => Promise<z.infer<T>>,
  options: { ttl?: Duration } = {},
): Promise<z.infer<T>> {
  const { ttl = "1h" } = options;
  const serializedKey = serializeKey(key);

  // 1. 先查 KV 缓存
  const kvData = await env.KV.get(serializedKey, "json")
    .catch(/* 容错 */);

  if (kvData !== null) {
    const result = schema.safeParse(kvData);
    if (result.success) return result.data;
  }

  // 2. KV 未命中，回源数据库
  const data = await fetcher();
  if (data === null) return data;

  // 3. 后台写入缓存，不阻塞响应
  context.executionCtx.waitUntil(
    set(context, key, JSON.stringify(data), { ttl }),
  );

  return data;
}

最难的问题：缓存失效

「计算机科学只有两个难题：缓存失效和命名。」—— Phil Karlton。这个项目用版本号失效优雅地解决了缓存失效问题。

CODE 
// 读取当前版本号
export async function getVersion(context, namespace) {
  const key = `ver:${namespace}`;
  const v = await context.env.KV.get(key)
    .catch(/* 容错 */);
  if (v && !Number.isNaN(Number.parseInt(v))) {
    return `v${v}`;
  }
  return "v1";
}

// 版本号 +1，旧缓存全部作废
export async function bumpVersion(context, namespace) {
  const key = `ver:${namespace}`;
  const current = await context.env.KV.get(key)
    .catch(/* 容错 */);
  let next = 1;
  if (current) {
    const parsed = Number.parseInt(current);
    if (!Number.isNaN(parsed)) next = parsed + 1;
  }
  await context.env.KV.put(key, next.toString());
}

三种缓存失效策略

缓存写入容易，失效才是难题。这个项目使用三种策略，每种适用于不同的场景。

🔄

版本号 bump

一次 bump 就能让整个命名空间的所有旧缓存失效。不知道有哪些 key 也没关系。用于文章发布、全站刷新等场景。

🎯

精确 key 删除

直接删除指定的缓存 key。精准、高效，但需要知道要删哪个 key。用于删除评论、更新单篇等场景。

🌍

CDN Purge API

调用 Cloudflare API 清除全球 CDN 缓存。代价最大但覆盖最全，用于站点级更新、域名切换等场景。

实际更新文章时，三种策略会组合使用：先 bump 版本号让 KV 缓存失效，再调用 CDN Purge API 清除边缘缓存。这就是为什么管理员更新文章后，全球用户很快就能看到最新版本。

      const identifier =
        getRequestHeader("cf-connecting-ip")
        || session?.user.id || "unknown";
      const uniqueIdentifier = `${identifier}:${scope}`;

      // 用 Durable Object 实现分布式限流
      const id = context.env.RATE_LIMITER
        .idFromName(uniqueIdentifier);
      const rateLimiter = context.env.RATE_LIMITER
        .get(id);

      const result = await rateLimiter
        .checkLimit(options);

      if (!result.allowed) {
        throw createRateLimitError(result.retryAfterMs);
      }

      return next();
    });
};

export async function handleQueueBatch(batch: MessageBatch, env: Env, ctx: ExecutionContext) {
  const pageviewBatch = [];

  for (const message of batch.messages) {
    const parsed = queueMessageSchema.safeParse(message.body);
    if (!parsed.success) {
      message.ack();
      continue;
    }

    try {
      const event = parsed.data;
      switch (event.type) {
        case "EMAIL":
          await handleEmailMessage({ env, executionCtx: ctx }, {
            ...event.data,
            idempotencyKey: message.id,
          });
          break;
        case "WEBHOOK":
          await handleWebhookMessage({ env }, event.data, message.id);
          break;
        case "POST_AUTO_SNAPSHOT":
          await handlePostAutoSnapshotMessage({ env }, event.data);
          break;
        case "PAGEVIEW":
          pageviewBatch.push({ data: event.data, message });
          continue;
        default:
          event satisfies never;
          throw new Error("Unknown queue message type");
      }
      message.ack();
    } catch (error) {
      message.retry();
    }
  }

  if (pageviewBatch.length > 0) {
    try {
      await handlePageviewMessages({ env }, pageviewBatch.map((item) => item.data));
      for (const item of pageviewBatch) item.message.ack();
    } catch (error) {
      for (const item of pageviewBatch) item.message.retry();
    }
  }
}

有些任务不是「扔进去就完事」那么简单。AI 评论审核需要按步骤执行、每步可重试、还能中途恢复——这就像引擎装配线，每一步都要验证后才能进入下一步。

export class CommentModerationWorkflow extends WorkflowEntrypoint<Env, Params> {
  async run(event: WorkflowEvent<Params>, step: WorkflowStep) {
    const { commentId } = event.payload;

    // 1. 获取评论
    const comment = await step.do("fetch comment", async () => {
      return await CommentRepo.findCommentById(db, commentId);
    });

    // 2. 获取帖子上下文
    const post = await step.do("fetch post and thread", async () => {
      return await PostRepo.findPostById(db, comment.postId);
    });

    // 3. AI 审核（可能失败，有重试）
    const moderation = await step.do(
      "moderate comment",
      { retries: { limit: 3, delay: "3 seconds", backoff: "exponential" } },
      async () => {
        const result = await moderateComment({
          comment: comment.content,
          post: { title: post.title, summary: post.summary },
        });
        return result;
      },
    );

    // 4. 根据 AI 判断更新状态
    await step.do("update comment status", async () => {
      if (moderation.shouldPublish) {
        await CommentRepo.updateCommentStatus(db, commentId, "published");
      } else {
        await CommentRepo.updateCommentStatus(db, commentId, "pending");
      }
    });

    // 5. 发送通知
    await step.do("send notification", async () => {
      // ...
    });
  }
}

关键洞察：快递 vs 审批流程

Queue 和 Workflow 的区别就像「快递」和「审批流程」。快递（Queue）是把包裹扔进系统，它会到的，但你不需要知道中间经过了哪些站点。审批流程（Workflow）是需要按步骤执行、每步可重试、可以中途暂停恢复的复杂流程。选错会导致任务丢失或重复执行。

📨

Queue 快递生产线

高吞吐、火后即忘。适合邮件、Webhook、浏览量等单步、高频的任务。

⚙️

Workflow 装配线

多步骤、可恢复、有状态。每步执行结果被持久化保存，失败后只需重做当前步骤。适合 AI 审核、文章发布、导入导出等复杂流程。

ADR-0004 明确定义了两者的边界：Workflows 用于有序、可恢复的持久化业务流程（文章处理、定时发布、导入导出）。Queues 用于高吞吐副作用（邮件、Webhook、浏览量、快照）。
